## 0. 文件定位

本文件是 TeamMatch 前端仓库的本地 AI 审查上下文。

它的目标不是让 AI 直接写代码，而是让 AI 明确：

1. TeamMatch 是什么项目；
2. 当前前端审查的真实目标是什么；
3. 哪些问题需要阻断 Gerrit Review；
4. 哪些问题只记录、不阻断；
5. DeepSeek-V4-Pro 与 Codex 如何协同审查；
6. 前端代码审查时必须遵守哪些业务口径；
7. AI 不得执行哪些 Git 写操作；
8. 如何输出最终可用于 Code Review 的结论。

本文件不是前端需求文档的替代品。  
若仓库内存在更完整的 `docs/design/system-design-v2.1.md`、接口文档、README、测试说明，应优先读取这些项目文件。  
若前端仓库中没有完整业务文档，则本文件作为最低限度审查依据。

4. 用户角色与审查定位

用户不是前端主开发。

用户当前在前端仓库中的真实角色是：

前端 Gerrit 守门人 + 风险记录员

用户主要负责：

拉取前端代码；
检查仓库是否干净；
检查是否污染仓库；
检查是否影响其他负责人继续开发；
检查是否破坏公共配置、公共路由、公共请求封装；
检查是否存在敏感信息；
借助 DeepSeek-V4-Pro 与 Codex 进行审查；
根据最终 AI 审查结论决定是否继续 Code Review；
对非阻断问题做记录，而不是强行卡死提交。

用户不是：

前端质量负责人；
前端架构师；
前端代码重构负责人；
UI 体验最终把关人；
替前端同学写代码的人。

当前前端审查标准应低于正式企业前端质量门禁。

审查目标是：

只拦截会污染仓库、影响别人、破坏主流程、导致项目打不开、泄露敏感信息的问题。

不应因为以下问题直接阻断：

页面样式粗糙；
组件拆分不优雅；
代码重复但范围局限于个人页面；
命名一般；
缺少 loading / empty / error 状态；
暂无自动化测试；
局部功能还没完全 polish；
mock 数据暂未替换，但没有影响他人开发；
Mock 阶段的局部行为还不完整，例如操作后只提示 toast、暂未更新本地状态；
部分业务分支或按钮场景覆盖不完整，但不影响他人继续开发；
真实接口预留代码后续联调前需要调整，但当前 mock 主流程不受影响；
局部 UI 资源缺失、鉴权闪屏、边界竞态等可后续修复的问题；
缺少截图或录屏证据。

这些属于非阻断问题，应该记录，但不默认阻止 Code Review。

5. 前端审查总原则

当前阶段前端审查只重点回答四个问题：

这个提交会不会污染仓库？
这个提交会不会影响其他负责人继续开发？
这个提交会不会破坏公共配置、公共路由、公共请求封装？
这个提交会不会明显违反 TeamMatch 的核心业务口径？

如果答案都是“否”，即使代码不够漂亮，也可以继续 Code Review。

前端审查不要过度追求：

最优组件设计；
最佳 UI 体验；
完整异常态；
大厂级代码规范；
完整自动化测试；
一次性实现所有页面。

前端审查当前更像“仓库安全检查 + 主线口径检查 + 协作影响检查”。

6. TeamMatch 主业务闭环

当前冻结的产品主线：

冷启动引流 → 正式档案建立 → 发布/搜索项目 → 邀请/申请组队 → 协作执行 → 项目结项 → 互评沉淀 → 信誉变化 → 影响下一次组队

这条链路是前端页面、接口、状态展示、交互入口的核心依据。

前端页面不应把 TeamMatch 做成普通信息展示 demo。

任何核心页面或流程都应能服务于：

用户进入平台；
浏览榜单或项目；
完成登录与认证；
建立正式档案；
发布或加入项目；
完成组队；
项目进行与结束；
项目结束后互评；
查看信誉分与变化记录；
举报、申诉、治理纠错。

9. 核心业务口径：用户与认证

普通用户：

通过微信登录；
后端换取 openid；
自动注册或直接登录；
返回 token + 用户信息；
用户填写学校邮箱；
发送验证码；
提交验证码；
成功后 email_verified = 1。

管理员：

使用 username + password 登录；
登录成功后返回 adminToken；
进入 Web 管理后台。

关键规则：

被封禁用户不能登录；
邮箱验证码需要防刷；
邮箱不能被多人重复绑定；
用户角色只能由后端控制，前端不能自行决定；
正式档案建立前，核心操作权限受限制。

前端审查关注：

是否把用户角色写死在前端；
是否绕过登录态判断；
是否绕过邮箱认证判断；
是否硬编码 token；
是否把未认证用户放进核心操作；
是否统一处理 401 / token 失效；
是否区分普通用户 token 与 adminToken。
10. 核心业务口径：正式档案与冷启动

冷启动主线：

排行榜引流 → 临时技术画像 → 邮箱认证 → 档案认领 → 正式榜单 / 搜索 / 组队主流程

冷启动不是附属营销动作，而是主流程入口的一部分。

P0 冷启动规则：

首页冷启动阶段优先展示技术榜单，而不是普通项目流；
临时技术画像遵循“先给结果，再要求认证”；
正式榜单准入依赖正式档案建立；
被搜索到依赖正式档案建立；
接收邀请依赖正式档案建立；
主动申请加入项目依赖正式档案建立；
技术画像只分析公开仓库信息；
P0 只支持 GitHub；
Gitee 双平台、批量爬取、长期画像沉淀表移入 P1；
技术画像不落核心主库；
无 GitHub 用户仍可正常组队，但不进入技术榜。

前端审查关注：

首页是否把冷启动入口完全删掉；
是否把冷启动做成孤立展示页，不承接认证/建档/组队；
是否把临时画像误认为正式档案；
是否让未建档用户进入正式榜单；
是否让未建档用户被搜索、被邀请、申请加入项目；
是否出现 Gitee P0 回流；
是否把冷启动相关数据写死成不可替换的假数据。
11. 核心业务口径：项目状态

项目状态统一使用英文枚举：

recruiting
in_progress
ended
eval_closed

含义：

recruiting：招募中；
in_progress：进行中；
ended：已结束，互评窗口开放；
eval_closed：互评关闭，只读状态。

前端不得自行创造另一套状态。

前端展示可翻译为中文，但数据判断必须对齐后端枚举。

关键规则：

只有 recruiting 状态允许邀请和申请；
项目开始后不允许继续加入；
项目结束后开启 7 日互评窗口；
eval_closed 后只读，不允许提交互评；
P0 不提供项目删除；
eval_closed 不是删除状态；
项目状态不表达软删除。

前端审查关注：

是否把状态写成中文参与逻辑判断；
是否把 eval_closed 当成删除；
是否在 in_progress / ended 仍允许申请加入；
是否在非 ended 状态允许互评；
是否在 eval_closed 后仍允许提交互评；
是否前端自行改变状态机。
12. 核心业务口径：组队请求

组队请求状态：

pending
accepted
rejected
cancelled
expired

关键规则：

邀请和申请统一走 team_request；
只有 recruiting 状态允许申请 / 邀请；
项目满员后不允许继续加入；
同一 pending 请求不允许重复创建；
接受后才建立正式成员关系；
项目开始后剩余 pending 请求失效；
被邀请对象必须已经建立正式档案；
用户申请加入项目前必须已经建立正式档案。

前端审查关注：

是否允许未建档用户申请；
是否允许未建档用户被邀请；
是否在项目非 recruiting 时仍展示可申请按钮；
是否没有处理 pending / accepted / rejected / cancelled / expired 的展示差异；
是否把邀请和申请做成两套完全冲突的口径。
13. 核心业务口径：成员状态与退出机制

成员状态：

active
exited

退出机制 P0 冻结口径：

team_member.exit_mode = self_exit / exit_vote
exit_vote.result = pass / reject / NULL
team_member.status = active / exited

含义：

self_exit：成员主动退出；
exit_vote：队长发起移除投票；
pass：投票通过；
reject：投票不通过；
NULL：投票中或被投票人中途 self_exit；
active：正常在队；
exited：已离队。

不再使用以下旧口径作为 P0 主流程：

有事退出
协商退出
无故退出
remove_vote
removed
队长直接移除
队长转让 P0

注意：

前端可以在展示文案中解释 negotiated / malicious 等处罚等级；
但不能把旧的“三档退出结果”重新作为 P0 主流程；
P0 不保留队长直接移除能力；
移除统一走 exit_vote；
队长不能在 P0 主流程里随意转让；
status='exited' AND exit_mode='exit_vote' 才能识别被移除成员。

前端审查关注：

是否出现旧三档退出主流程；
是否出现 remove_vote / removed；
是否允许队长直接移除成员；
是否允许 ended / eval_closed 后继续成员变更；
是否把 self_exit 与 exit_vote 混用；
是否投票失败仍把成员改成 exited；
是否绕开投票结果直接改状态；
是否影响后端接口对接。
14. 核心业务口径：互评

评价状态：

normal
pending_review
voided
kept_no_credit

互评核心规则：

仅同项目正式成员可互评；
不能评价自己；
同一项目内同一对象只能评价一次；
项目必须处于 ended；
必须在互评窗口内；
互评窗口固定为项目结束后 7 日；
四维评分：沟通协作、任务完成、技术能力、责任心；
1 分 / 2 分必须附负向标签和说明；
5 分必须附正向标签；
命中异常规则进入 pending_review；
pending_review 不直接计分；
单项目信誉分影响封顶；
前台互评匿名展示；
后台可追溯。

前端审查关注：

是否允许自评；
是否允许重复评价；
是否在非 ended 状态开放互评；
是否超过 eval_deadline 仍允许互评；
是否四维评分被砍成一维；
是否低分不要求负向标签和说明；
是否 5 分不要求正向标签；
是否把 pending_review 当 normal 展示；
是否把 pending_review 直接计分；
是否暴露具体评价者身份；
是否让前端自行计算并直接修改信誉分。
15. 核心业务口径：信誉分

信誉分初始值：

100

信誉分变化应基于后端计算结果和 credit_change 流水。

前端原则：

前端展示信誉分；
前端展示信誉分变化记录；
前端不应自行决定最终信誉分；
前端不应绕开 credit_change；
前端不应暴露具体谁给了某次评分；
前端展示变化摘要即可。

前端审查关注：

是否写死信誉分；
是否前端直接计算并当作最终结果；
是否暴露具体评价者；
是否忽略 effective / pending_review；
是否把已挂起的流水当作已生效；
是否没有区分 normal / pending_review / voided / kept_no_credit。
16. 核心业务口径：举报、申诉、治理

举报：

P0 举报对象范围是 user / project；
不支持将 evaluation 作为 report.target_type；
举报状态应有 pending / resolved / dismissed 等处理状态；
举报处理需要留痕。

申诉：

申诉对象必须明确；
同一恢复事件只能生效一次；
申诉通过后执行恢复逻辑，而不是只改显示文案；
申诉处理结果要回流到信誉分或相关状态。

后台治理：

板块管理；
举报处理；
申诉处理；
异常评价复核；
处罚管理；
档案审核；
信誉分审计。

前端审查关注：

是否把 evaluation 放入 report.target_type；
是否申诉通过只改前端文案；
是否没有状态展示；
是否管理端和用户端 token 混用；
是否管理员权限前端写死；
是否治理操作没有留痕入口。

https://{domain}/api

管理端 Base URL：

    "total": 0,
    "page": 1,
    "pageSize": 20
  }
}

统一失败响应：

{ "code": 400, "message": "参数错误", "data": null }

常见错误码：

400 参数错误
401 未登录 / token 无效
403 无权限
404 资源不存在
409 状态冲突 / 重复操作
422 业务规则不满足
500 服务异常

前端审查关注：

是否只看 HTTP 200；
是否忽略 code；
是否没有统一处理 message；
是否没有统一处理 401；
是否没有统一处理 403；
是否没有处理 409 / 422；
是否每个页面重复写 wx.request；
是否硬编码 token；
是否用户端和管理端 baseURL 混用；
是否没有封装 Authorization。

原生微信小程序项目通常应包含：

app.js
app.json
app.wxss
pages/
utils/
project.config.json
sitemap.json

常见页面文件成组出现：

index.js
index.json
index.wxml
index.wxss

若存在 components，应检查组件是否被正确引用。

若存在 utils/request.js 或类似文件，应检查请求封装。

若存在 package.json，才按 npm 工程进一步审查。

当前没有 package.json 时，不要默认执行 npm install。

前端审查关注：

app.json 是否存在；
app.json 的 pages 路由是否能对应真实 pages 文件；
app.js 是否只做全局初始化；
app.wxss 是否只做全局样式；
pages 是否有成组页面文件；
utils 是否包含可复用工具；
是否有公共请求封装；
是否误提交 node_modules；
是否误提交 dist；
是否误提交临时文件；
是否误提交 IDE 文件；
是否误提交个人配置。
19. project.private.config.json 审查

project.private.config.json 通常是微信开发者工具个人本地配置。

它不是看到就一定阻断，但必须检查：

是否包含私人 appid；
是否包含个人路径；
是否包含开发者私有配置；
是否包含账号信息；
是否应该加入忽略列表；
是否影响其他人打开项目。

判断标准：

如果包含敏感信息或个人路径，属于阻断问题；
如果只是无敏感的开发者工具默认配置，可作为非阻断问题记录；
后续建议放入本地忽略，但不要随意修改 .gitignore，除非团队决定。
20. 阻断问题定义

只有以下问题建议阻断 Gerrit Review：

20.1 仓库结构阻断
仓库无法被识别为前端项目；
小程序基础结构损坏；
缺少 app.json 且无其他说明；
app.json 路由指向不存在页面；
页面文件缺失导致小程序打不开；
修改后微信开发者工具无法打开项目；
当前 Change 导致其他页面无法进入。
20.2 仓库污染阻断
提交 node_modules；
提交 dist / build 产物；
提交大量临时文件；
提交 IDE 缓存；
提交系统文件；
提交无关大文件；
一次 Change 混入大量无关功能，无法审查。
20.3 敏感信息阻断
硬编码 token；
硬编码账号；
硬编码密码；
硬编码私人 appid；
硬编码个人路径；
泄露后端真实密钥；
泄露管理员账号；
泄露个人开发者配置。
20.4 协作影响阻断
修改公共请求封装导致其他页面请求失效；
修改公共配置导致其他负责人无法继续开发；
修改公共组件导致其他页面崩溃；
修改 app.json 破坏他人页面路由；
修改公共状态枚举导致前后端接口对不上；
删除他人页面；
大范围格式化导致 diff 难以审查。
20.5 业务口径阻断
明显旧口径回流并影响接口对接；
使用“有事退出 / 协商退出 / 无故退出”作为 P0 主流程；
使用 remove_vote / removed 作为 P0 主流程；
队长直接移除成员；
前端绕过正式档案限制；
未登录、未认证、未建档用户可执行核心操作；
非 ended 项目开放互评；
pending_review 评价被当作 normal 计分；
前端自行改信誉分；
暴露具体评价者身份导致匿名互评失效。

注意：功能设计缺口、Mock 阶段交互不完整、操作后本地状态未同步、按钮场景覆盖不全、真实接口预留写法待改、快速切换等边界竞态，默认不单独作为阻断问题。
只有当这些问题会导致当前主流程不可用、影响其他负责人继续开发、破坏公共配置 / 公共路由 / 公共请求封装，或明显违反 TeamMatch 核心业务口径时，才升级为阻断问题。

如果存在阻断问题，建议 Gerrit 投票为：

-1 或 0

具体取决于问题严重性和团队习惯。

21. 非阻断问题定义

以下问题原则上不阻断当前 Code Review，只记录到审查记录中：

页面样式粗糙；
UI 不够美观；
组件拆分不优雅；
代码命名一般；
存在局部重复代码；
缺少 loading 状态；
缺少 empty 状态；
缺少 error 状态；
暂无自动化测试；
Mock 阶段操作只做 toast，尚未真正调用 service 或同步本地状态；
请求按钮、状态变体、异常分支等功能覆盖不完整；
真实接口预留写法后续联调前需要修正；
快速切换、重复点击等边界场景存在可修复缺陷；
局部鉴权展示有闪屏风险，但没有真实敏感数据泄露；
局部图标、图片、视觉资源缺失或路径待修；
没有截图或录屏证据；
mock 数据暂未替换真实接口；
局部页面功能不完整，但不影响公共流程；
局部 console.log；
注释不够完善；
文案不够精细；
页面跳转体验一般；
CSS / WXSS 不够规整；
非公共页面内部实现比较粗糙。

这些问题应记录，但不应默认卡死提交。

建议写入：

.ai/FRONTEND_REVIEW_FEED.md

该文件也应为本地文件，不提交 Gerrit。

22. Gerrit 投票建议标准
+2

满足：

无阻断问题；
没有影响其他负责人继续开发；
没有导致项目或主流程打不开；
没有破坏公共配置、公共请求封装或 app.json 路由；
没有敏感信息泄露；
没有明显仓库污染或无关大文件；
不违反核心业务口径。

当前开发过渡阶段，若只是存在功能设计不完整、Mock 行为不够真实、局部状态同步缺失、按钮场景覆盖不全、接口预留写法待联调修正、局部 UI 资源缺失等小问题，应记录为后续整改项，仍可给 +2。
+1

适用：

没有明确阻断问题，但 reviewer 对运行结果、审查范围或协作影响仍有不确定；
需要其他负责人再确认；
暂时只表示方向认可，不作为最终通过票。
0

适用：

信息不足；
无法确认是否可运行；
当前只做记录，不投明确赞成/反对；
等待前端负责人补充说明。
-1

适用：

存在阻断问题；
需要前端负责人修改后重新提交 Patch Set；
但问题不是恶意或不可接受。
-2

适用：

严重污染仓库；
泄露敏感信息；
大量无关提交；
明显破坏主线且拒不修复；
需要明确阻止合入。

一般课程项目中，优先使用 -1，而不是轻易 -2。

23. DeepSeek 与 Codex 双模型审查机制
23.1 基本原则

DeepSeek-V4-Pro 和 Codex 都需要参与审查。

二者不是简单的“初审 / 复审”关系，而是：

第一轮：分别独立审查
第二轮：互相读取报告，进行交叉复核
最终：由 Codex 输出最终裁决
23.2 第一轮独立审查

DeepSeek 第一轮：

只读本文件；
只读当前代码；
只读当前 diff；
只读可用项目文档；
不读取 Codex 报告；
不修改文件；
不执行 Git 写操作；
输出 DeepSeek 独立报告。

Codex 第一轮：

只读本文件；
只读当前代码；
只读当前 diff；
只读可用项目文档；
不读取 DeepSeek 报告；
不修改文件；
不执行 Git 写操作；
输出 Codex 独立报告。
23.3 第二轮交叉复核

第一轮完成后：

DeepSeek 可以读取 Codex 报告；
Codex 可以读取 DeepSeek 报告；
DeepSeek 复核 Codex 是否漏掉敏感信息、结构问题、体验问题；
Codex 复核 DeepSeek 的阻断判断是否过严或过松；
最终由 Codex 输出裁决。
23.4 模型权重

Codex 默认权重更高。

Codex 主要负责：

技术正确性；
业务一致性；
工程边界；
Gerrit 是否可通过；
是否影响其他负责人；
是否破坏公共流程；
是否存在真正阻断问题。

DeepSeek-V4-Pro 主要负责：

广角扫雷；
敏感文件；
仓库结构；
明显体验问题；
明显疏漏；
非阻断问题补充。

若两者冲突：

默认以 Codex 交叉复核后的最终结论为准；
但 DeepSeek 指出的敏感信息、仓库污染、无法运行、影响他人开发问题必须复核；
不允许因为 DeepSeek 说“代码不优雅”就阻断；
不允许因为 Codex 没提敏感信息就忽略 DeepSeek 的敏感信息提醒。

29.1 无阻断问题，通过
