# TeamMatch AI 通用入口

本文件是 Codex、Claude Code、Cursor、Kiro 等 AI 工具进入 TeamMatch 项目的通用入口。

## AI 进入后读取路由

**读取本文件后，按用户说的任务类型走对应路径。不要自己猜要读哪些文件——下面已经写死了。**

### 如果用户说"开发 M{N}"（如 M5、M8、M9）

**先判断是续建还是新建：检查 `M{N}_WORK_ORDER.md` 或 `docs/m{n}/` 目录是否存在。**

#### 续建（文件存在）

```
1. docs/design/system-design-v2.1.md（§0.3 冻结规则、§0.4 P0/P1 边界、对应板块章节、§8 全局约束、§9.1 事务边界）
2. M{N}_WORK_ORDER.md
3. docs/m{n}/M{N}_CONTEXT.md
4. docs/m{n}/M{N}_TODO.md
5. IMPLEMENT_LOG.md（最近一段）
```

#### 新建 / 冷启动（文件不存在）

```
1. docs/design/system-design-v2.1.md（重点读该模块对应章节 + §8 全局约束 + §9.1 事务边界）
2. sql/schema.sql（确认该模块的数据库表、字段、约束）
3. 参考已有模块的文档结构作为模板：
   - 找最近的 M{N}_WORK_ORDER.md 看工作令格式
   - 找最近的 docs/m{n}/ 目录看 CONTEXT/TODO/TEST_PLAN 格式
4. 列出以下待创建的文件，等用户确认后再动手：
   - M{N}_WORK_ORDER.md
   - docs/m{n}/M{N}_CONTEXT.md（精简规则）
   - docs/m{n}/M{N}_TODO.md（任务拆解）
   - docs/m{n}/M{N}_TEST_PLAN.md（测试计划）
```

**通用原则：如果对应文件不存在，跳过不报错。不要因为缺文档就停止——先读 V2.1 和 schema.sql，边做边补文档。**

### 如果用户说"审计"、"审查"、"code review" 或 "review"（Gerrit Change）

**只要用户给出 Change-Id、Gerrit Change、patchset、commit 标题，或语境是在审计/审查某个 Gerrit 变更，就必须走本路径。不要因为用户说的是"审计"而落到"其他任务"路径。**

```
1. docs/review/gerrit-review-rules.md  ← 必须先读！含 Gerrit SOP、Windows sandbox 规避和反模式清单，避免做无用查找
2. docs/design/system-design-v2.1.md（§0.4 冻结基线、§8 reasonCode、对应板块章节）
3. docs/m{n}/M{N}_CONTEXT.md（仅当 change 涉及具体模块时）
```

然后执行审查 SOP（gerrit-review-rules.md 第 5 条）：
```text
0. curl -s "https://<user>:<pass>@（已脱敏）/a/changes/?q=<Change-Id>" 获取 change number
   └─ 返回值中 "_number" 字段即 change number，如 3233
   └─ ref 路径 = refs/changes/<末两位>/<change_number>/<patchset>（如 refs/changes/33/3233/2）
1. git ls-remote 确认目标 ref 存在
2. git fetch 拉取缺失 ref
3. git diff 获取变更内容
4. 按 AGENTS.md Code Review 标准逐项检查
5. 输出三段式 Review 结论（阶段性成果 / 必须现在处理 / 记录后补）
```

**关键约束：不要跳过 gerrit-review-rules.md 直接操作 Gerrit。不要猜 ref 路径。不要对 merge commit 用 diff-tree。Change-Id 不是 ref 路径组成部分——必须先通过 Gerrit API 查到 change number 才能构造 ref 路径。Java 源码在 `src/main/java/com/teammatch/`，不要猜 `org/example/backend/` 或其他包路径。**

**Windows sandbox 约束：Gerrit 审计/审查时，不要先查本地分支状态、不要先做 memory 扩展检索、不要先建 worktree 或跑测试、不要并行大范围读取文件。先按 `docs/review/gerrit-review-rules.md` 的最短路径定位 Gerrit ref 和 diff，再按需补证据。**

### 如果用户说其他任务（重构、排查、问询）

```
AGENTS.md → docs/design/system-design-v2.1.md → 按模块读对应源码
```

## 项目定位

TeamMatch 是面向校园场景的组队与互评平台。

产品形态：

- 微信小程序用户端
- Web 管理后台

核心闭环：

```text
冷启动引流 → 正式档案建立 → 发布/搜索项目 → 邀请/申请组队 → 协作执行 → 项目结项 → 互评沉淀 → 信誉变化 → 影响下一次组队
```

## 技术栈

- 微信小程序原生
- Spring Boot
- MySQL 8.0
- Redis
- 阿里云 ECS
- Gerrit
- Jenkins

## 开发流程

1. 先读 `docs/design/system-design-v2.1.md`
2. 按任务类型读取对应提炼文档
3. 开发前确认是否涉及冻结规则
4. 涉及公共字段、状态机、退出规则、互评规则、信誉流水、申诉恢复、冷启动前置条件时，必须先提示需要全组对齐
5. 实现时只改与任务直接相关的文件
6. 完成后追加更新 `IMPLEMENT_LOG.md`

## 测试要求

后续开发必须保留测试证据。重点覆盖：

- 单元测试：信誉分、项目级封顶截断、退出结果计算
- 接口测试：状态流转、资格校验、错误码、幂等性
- 端到端测试：登录/认证、项目发布/状态流转、邀请/申请/加入、退出认定、互评、举报/申诉/处罚闭环
- Jenkins 或等价 CI 证据

不能提交缺少必要测试说明的核心链路改动。

## Code Review 通过标准

审查不是判卷，不追求一次性 100%。审查目标是保护团队协作节奏：

```text
基底好就给过；
安全漏洞、公共契约破坏、V2.1 冻结规则冲突，一个不放过；
其余问题只要不影响别人开发，就记录后补。
```

审查结论只分两类，不打分：

- 阶段性通过
- 暂不通过

其中“阶段性通过”可以附带“需记录后补”。不要使用 `60/100`、`80/100` 这类评分表达，避免把 Review 变成对组员的审判。

### 先判断是否是好基底

一个阶段性提交是否合格，不看它有没有做到最终完整闭环，而看两点：

1. 是否为下一轮开发提供了稳定落点，例如接口入口、DTO、Service 调用链、基础错误码、基础文档已经到位。
2. 是否诚实标注当前限制，不能把“骨架已完成”包装成“完整业务闭环已完成”。

只要能支撑后续开发，且没有误导他人依赖未完成能力，就应先肯定它是好基底。

### 必须阻塞合入的问题

只有这些问题应阻塞：

- 编译失败、启动失败、公共测试失败。
- 会导致其他模块或前端按文档联调失败。
- 破坏数据库字段、唯一约束、状态机、`reasonCode` 等公共契约。
- 违反 V2.1 冻结规则，并且会影响其他人按冻结口径继续开发。
- 权限边界、安全边界明显缺失。
- 阶段性能力没有说明限制，却在文档或提交说明中表现为完整可用。

### 记录后补的问题

这些问题要指出，但不应直接否定阶段性成果：

- 错误码覆盖还不完整。
- 某些边界校验还没补齐。
- 测试覆盖不足。
- commit type 不够准确。
- Controller 强依赖实现类。
- `JWT_SECRET` 等配置硬编码。
- 方法放实体类还是工具类。
- trailing whitespace。
- 新接口自身体验问题，但不影响别人依赖。

前提是：这些问题不破坏公共契约、不影响别人继续开发，并且要有记录位置，例如提交说明、文档“已知限制”、TODO、Issue、IMPLEMENT_LOG。

### 冻结规则与非冻结问题

V2.1 冻结规则、状态机、角色边界、信誉分流水、`reasonCode`、schema 约束属于公共协作地基，不能静默破坏。

代码风格、架构偏好、提交类型、硬编码等属于质量改进，不应和公共契约问题同级处理。

### 推荐 Review 输出格式

每次审查按这个顺序写：

```text
结论：阶段性通过 / 暂不通过

阶段性成果：
- 这轮已经完成了什么。
- 对后续开发有什么价值。

基底判断：
- 当前是否是一个可继续开发的好基底。
- 为什么。

必须现在处理：
- 只列会影响别人开发、公共契约、安全边界、V2.1 冻结口径的问题。

记录后补：
- 错误码细节。
- 边界校验。
- 测试。
- 文档完善。
- 代码组织优化。
- **仅列出有功能正确性、安全性、性能影响的实质性建议，代码风格、注释排版、XML 格式偏好等非功能性差异不列入。**
- **如无实质性建议，直接写"无"，禁止为填空而凑条目。**

建议下一步：
- 本轮合入前做什么。
- 下一轮优先补什么。
```

### 行内 Comment 与总 Reply 分工

如果审查问题可以明确落到某个文件的某一行或相邻几行，应优先给出行内 comment 建议，方便在 Gerrit 对应位置直接评论。

行内 comment 只用于指出清楚、重要、改动较少即可修复的问题，例如：

- 某个端点遗漏 `try-catch`，导致不能统一返回 `Result<T>`。
- 某一行硬编码值违反 V2.1 冻结规则。
- 某个条件判断缺失，导致状态机、权限边界或事务副作用错误。

不要为了凑数量逐行评论。以下内容一般放在总 reply，不强行塞进行内 comment：

- 父 change 遗留问题。
- 合入顺序、rebase、依赖链提醒。
- 测试结果和整体风险判断。
- 需要跨多个文件理解的设计问题。

推荐输出顺序：

1. 先列行内 comment 建议，格式为 `文件路径:行号` + 问题原因 + 修复方向。
2. 每个需要评论的文件列完后，再给总的 Code-Review reply。
3. 如果没有适合行内评论的问题，明确写“行内 comment 建议：无”。

### 组长口吻

Review 代表组长态度，应该先肯定真实成果，再指出差距，而不是只列缺陷。

合适的表达：

```text
这轮已经把 M3 的接口骨架和主要调用链搭起来了，可以支撑后续联调，是有价值的阶段性成果。

但为了不影响其他组员，以下公共契约/安全边界问题需要先处理。

其余问题不影响当前协作，记录后补。
```

不合适的表达：

```text
你没做到 A、没做到 B、没做到 C，所以不给过。
```

一句话版：

```text
先肯定基底，再说明差距；只卡公共协作风险，其余记录后补。
```

### 交叉审查协议（多 AI 协同）

当同时使用多个 AI 工具审查同一个 commit 时，审查结果应通过标准收敛而非立场博弈。核心原则：**标准收敛，不权威服从。**

#### 发起人操作规则

发起人是唯一能传递 AI 间信息的人，必须遵守以下约束防止审查污染：

**禁止的做法：**

- "DS 给了 +2，你觉得呢？" → **传递结论**，触发锚定效应
- "DS 看了你的也同意 -1" → **用另一个 AI 的立场施压**
- "Claude 说这里有问题，你确认一下" → **透露倾向**
- 第一轮审查前，向任何一个 AI 透露另一个 AI 的审查结论或倾向

**正确的做法：**

- 第一轮：两个 AI 只拿到 commit diff 和项目规范（AGENTS.md + V2.1），独立产出审查，不被告知对方存在或结论
- 第二轮：发起人提取**具体分歧点**（不是 ±2 整体结论），以中性问题抛给双方

> 示例："关于 `M4_LEADER_CANNOT_EXIT` 的文案是否构成 V2.1 冻结规则冲突，请对照 AGENTS.md 阻塞标准逐条论证。"

- 第三轮：如果仍有分歧，追问归因——"分歧落在标准解读的哪一步？是事实遗漏还是阈值判断不同？"
- 终局：发起人裁量，依据裁量规则表

#### AI 响应规则

收到另一个 AI 的审查结论（由发起人传递）时：

**必须做的：**

1. 对齐事实层：检查对方是否提到了我没看到的代码路径、异常分支、或规范条文。如有 → 补充阅读，更新事实认知
2. 对齐标准层：把双方的分歧点逐一映射到 AGENTS.md 阻塞条件，判断哪个分歧真正落在标准边界上
3. 逐条反馈：对每个分歧点给出明确判断——"同意对方，因为……"或"维持我方，因为……"，每条后面附标准依据
4. 重新论证而非重新站队：看到对方结论不同时，对标 AGENTS.md 逐条论证，讲清楚为什么达到/没达到阻塞阈值

**禁止做的：**

- 看到对方结论不同，立刻说"我认可你的判断，我改结论"（没有重新论证的改结论 = 权威服从）
- 被用户反驳后立刻 180 度翻转（同上）
- 被用户反驳后死硬不改（拒绝吸收新信息）
- 把审查变成 AI 之间的立场博弈

#### 裁量规则表

发起人在终局时按以下规则裁定：

| 分歧类型 | 裁量规则 |
|----------|----------|
| 事实遗漏 | 补读代码后自动收敛，以代码实际行为为准 |
| 事实错误 | 核验代码后自动撤销，错误依据的 -1 不成立 |
| 标准解读不同 | 以 AGENTS.md 明文优先，不推断"隐含精神" |
| 阈值判断（阻塞 vs 记录后补） | 只要一方能引用冻结规则 + 论证"影响他人开发"，-1 成立 |

最后一行的含义：**推翻 -1 需要证据（证明"不影响他人开发"），不能仅凭"我觉得不严重"推翻有理有据的 -1。**

#### 记录后补判断三问

每条候选问题过三道筛子：

1. 是否影响功能正确性、安全性、或公共契约？→ 否 → 不列入（风格/排版/命名偏好不列）
2. 是否已有记录位置（另一个 commit、已知 Issue、之前审查的记录后补）？→ 是 → 不重复列
3. 修复成本是否显著低于合入后纠正的成本？→ 是 → 列入；否 → 可以不列

禁止为凑条目把同一个问题拆成多条，也禁止把"以后可能有用"的泛泛建议塞进去。无实质性内容直接写"无"。

#### 行内 comment 行号规则

行内 comment 的行号必须来自实际源文件（Read 工具读取后的行号），不能从 diff 推算。没有把握的行号宁可不开行内 comment，放到总 Reply 的记录后补里。

## 文档拆分原则

当前不强制把“开发规则”和“审查规则”拆成不同 Markdown 文件。`AGENTS.md` 作为 AI 工具统一入口，必须保留最高优先级规则、开发流程和审查通过标准。

只有当 Review 规则扩展为详细检查清单、模板或案例库时，才需要单独维护 `REVIEW_GUIDE.md`；即使拆分，`AGENTS.md` 也必须保留摘要和入口链接。

## Review 回复模板

Gerrit Code-Review 回复按三段式输出，不硬夸不硬贬，不加"结论："前缀：

```text
Code-Review: +2 / -1

阶段性成果：
- 已完成的具体改动，列出要点

（-1 时加这段）必须现在处理：
- 阻塞合入的具体问题+w修复方向

记录后补：
- 不影响联调、下轮补的问题清单
```

规则：
- 三项标题固定：阶段性成果 / 必须现在处理 / 记录后补
- 阶段性成果只列事实，不加形容词（不写"远超预期""扎实""优秀"）
- 必须现在处理只写阻塞项，每一项说清"什么问题"+"修复方向"
- 记录后补只列实质性建议（功能正确性、安全性、性能），代码风格/排版等非功能性差异不列入
- 记录后补如无实质性内容，直接写"无"，禁止为填空而凑条目

- 提交前必须自测相关链路
- 提交说明必须写清影响范围
- 涉及接口、数据库、状态机、事务、`reasonCode` 的改动必须在提交说明中单独标注
- 合并前应具备 Review 记录和 Jenkins Verify 证据

## 本地分支约定

本仓库本地分支用途固定如下，所有 AI 工具必须遵守：

- `master` 只作为 `origin/master` 的本地镜像，用于查看和同步远程最新主干，不在 `master` 上写业务代码。
- 后续功能开发必须从最新 `master` 新建独立开发分支，例如 `m5-dev`。
- Git 分支是完整项目快照，不是只包含某个模块的文件夹。`m5-dev` 必须保留完整项目代码；所谓“只开发 M5”指提交差异只应包含 M5 相关改动，不能为了隔离 M5 而删除或不引入 M4/M6/公共配置等主干文件。
- 新建功能分支时，刚创建的功能分支应与 `master` 完全一致；开始开发后，通过 `git diff --name-status master..当前分支` 检查实际改动范围。
- 同步远程主干时，只允许在确认工作区干净后，对 `master` 执行：

```bash
git switch master
git fetch origin
git reset --hard origin/master
```

- 禁止在功能开发分支上执行 `git reset --hard origin/master`。
- 功能分支需要吸收最新主干时，应先同步 `master`，再在功能分支上显式 `rebase master` 或按任务要求处理。
- `backup/*` 分支只作为旧 patch set 或整理前状态的保险备份，未经用户明确确认不得删除。
- 执行任何分支切换、reset、删除分支、rebase、merge 前，必须先查看 `git status` 和当前分支用途，避免把个人开发分支、主干镜像分支和备份分支混用。
