## 2. 当前开发目标

当前不是开发完整 TeamMatch 系统。

当前只开发 M5 模块的第一批小业务闭环：

> 项目结束后的互评入口判断、待评价成员列表判断、最终提交前资格兜底校验。

本阶段目标不是写完整提交互评事务，也不是写信誉分计算。

本阶段要先把“谁应该看到互评入口、进入互评页后能评价谁、最终提交时如何兜底防止非法评价”这三件事写清楚、写小、写可测。

## 3. M5 第一阶段业务拆分

### M5-1A：项目级互评入口判断

业务问题：

> 当前用户打开首页、我的项目或项目详情页时，系统要不要给他展示“待互评 / 去互评”的入口？

自然语言规则：

1. 当前用户必须是该项目的正式成员；
2. 项目状态必须为 ended；
3. 当前时间必须仍在项目结束后的 7 天互评窗口内；
4. 满足以上条件时，该项目对当前用户具备进入互评页的资格；
5. 如果不满足以上任一条件，不展示互评入口。

这一层只判断“项目对当前用户是否处于可互评阶段”。

这一层不判断具体评价谁。

---

### M5-1B：待评价成员列表判断

业务问题：

> 当前用户进入某个项目的互评页后，系统应该展示哪些队友可以被他评价？

自然语言规则：

1. 列表来源必须是该项目的正式成员；
2. 当前用户本人不能出现在可评价对象中；
3. 当前用户已经评价过的成员，应标记为“已评价”或从待评价列表中排除；
4. 只有当前用户尚未评价过的其他正式成员，才显示为“去评价”；
5. 当所有其他成员都已评价完时，该项目对当前用户应显示为“互评已完成”。

这一层解决“进入互评页后，能评价谁”。

---

### M5-1C：最终提交前资格兜底校验

业务问题：

> 用户真正提交某个评价前，后端必须最后确认这次评价是否合法。

自然语言规则：

即使前端已经展示过入口和待评价成员列表，提交时后端仍必须兜底校验：

1. 当前用户仍然是该项目正式成员；
2. 被评价用户仍然是该项目正式成员；
3. 项目仍然处于 ended；
4. 当前时间仍在互评窗口内；
5. 评价人不能评价自己；
6. 评价人不能重复评价同一项目中的同一目标成员。

这一层不是为了正常页面展示，而是为了防止：

1. 页面缓存；
2. 多设备重复提交；
3. 用户重复点击；
4. 前端传错参数；
5. 用户绕过前端直接请求接口；
6. 互评窗口刚好过期；
7. 非成员访问；
8. 自评；
9. 重复评价。

## 5. 开发方式硬约束

### 5.1 不允许一次性生成全部文件

Claude Code 不允许一次性生成完整 M5-1A / M5-1B / M5-1C 的全部代码。

每次最多只能创建或修改一个文件。

每完成一个文件，必须立即停止，并向用户说明：

1. 本次创建或修改了哪个文件；
2. 这个文件解决什么业务问题；
3. 这个文件对应 M5-1A / M5-1B / M5-1C 中的哪一部分；
4. 这个文件中最重要的逻辑是什么；
5. 用户需要理解哪些点；
6. 下一步建议创建或修改哪个文件；
7. 等用户确认后才能继续。

用户未确认前，不得继续写下一个文件。

---

### 5.2 每个文件都要让用户参与理解

Claude Code 写完每个文件后，必须用自然语言解释：

1. 这个文件为什么存在；
2. 如果没有这个文件，会缺什么；
3. 这个文件和业务逻辑的对应关系；
4. 哪些地方可能需要用户决策；
5. 哪些地方是根据 system-design-v2.1.md 和 schema.sql 固定下来的，不能随便改。

如果用户表示不理解，Claude Code 必须先解释，不得继续写代码。

---

### 5.3 不允许顺手扩展

Claude Code 不得因为“顺手”而扩展范围。

禁止行为包括：

1. 写完 Service 后顺手写 Controller；
2. 写完资格判断后顺手写提交互评；
3. 写完评价判断后顺手写 credit_change；
4. 写完 M5 代码后顺手改 schema.sql；
5. 写完后端后顺手写前端；
6. 为了测试方便自行新增大量无关类；
7. 为了“架构完整”大规模重构项目结构。

本阶段追求小步、可理解、可测试、可审查。

## 6. 推荐文件生成顺序

Claude Code 必须先读取当前项目结构，再给出实际文件位置。

如果当前项目结构允许，推荐顺序如下：

1. 先创建 reasonCode / 结果枚举类；
2. 再创建项目级互评入口判断结果对象；
3. 再创建 M5-1A 项目级入口判断 Service；
4. 再创建 M5-1A 单元测试；
5. 再创建 M5-1B 待评价成员列表 DTO / Result；
6. 再创建 M5-1B 查询 Service；
7. 再创建 M5-1B 单元测试；
8. 再创建 M5-1C 最终提交前资格兜底 Service；
9. 再创建 M5-1C 单元测试。

但具体文件名和包路径必须根据当前项目已有结构决定。

禁止在未检查项目结构的情况下直接猜包名、猜目录。

## 7. 代码质量要求

### 7.1 业务表达清楚

代码应当让人能看出业务含义。

禁止写只有作者自己懂的缩写。

例如：

推荐：

- evaluation
- evaluator
- target
- project
- eligibility
- deadline

不推荐：

- eva
- tar
- p
- flag1
- checkA

---

### 7.2 判断逻辑要清楚

判断顺序必须符合业务含义：

1. 先判断项目级条件；
2. 再判断成员关系；
3. 再判断具体评价对象；
4. 最后判断重复评价。

不要把所有判断写成一坨难以理解的嵌套 if。

---

### 7.3 不要过度设计

本阶段不需要复杂设计模式。

不需要引入：

1. 策略模式；
2. 责任链模式；
3. 事件总线；
4. 消息队列；
5. 定时任务；
6. 分布式锁；
7. 复杂缓存；
8. 复杂权限框架。

简单、清楚、可测优先。

---

## 8. 测试要求

### 8.1 本阶段优先使用 JUnit

本阶段主要测试 Service 业务规则。

不使用 Postman 作为第一测试方式。

原因：

1. 当前先写后端业务内核；
2. Controller 不是本阶段重点；
3. Service 规则用 JUnit 更容易覆盖边界情况；
4. JUnit 更适合作为 Gerrit / CI 证据。

---

### 8.2 M5-1A 至少覆盖

项目级互评入口判断至少测试：

1. 用户是项目成员，项目 ended，未过互评窗口：允许展示入口；
2. 用户不是项目成员：不允许展示入口；
3. 项目不是 ended：不允许展示入口；
4. 已超过互评窗口：不允许展示入口。

---

### 8.3 M5-1B 至少覆盖

待评价成员列表至少测试：

1. 列表不包含当前用户本人；
2. 列表能识别尚未评价的队友；
3. 列表能识别已经评价过的队友；
4. 所有队友都评价完时，返回互评已完成状态；
5. 非 active 成员不应作为可评价对象。

---

### 8.4 M5-1C 至少覆盖

最终提交前资格兜底至少测试：

1. 正常允许提交；
2. 自评被拒绝；
3. 项目未结束被拒绝；
4. 互评窗口关闭被拒绝；
5. 评价人不是项目正式成员被拒绝；
6. 被评价人不是项目正式成员被拒绝；
7. 重复评价被拒绝；
8. 项目不存在被拒绝。

---

## 9. 用户参与方式

用户不是旁观者。

Claude Code 每完成一个文件后，必须等待用户确认。

用户需要参与以下事项：

1. 确认业务逻辑是否符合预期；
2. 确认文件职责是否能理解；
3. 确认命名是否能接受；
4. 确认是否继续下一个文件；
5. 在测试失败时阅读失败信息；
6. 在 Codex 审查前理解代码结构；
7. 最终亲自检查 git diff；
8. 最终亲自执行所有 Git 写操作。

如果用户没有确认，Claude Code 不得继续下一步。

---

## 10. Git 操作硬禁令

Claude Code 绝对禁止执行以下命令：

1. git add
2. git commit
3. git push
4. git reset
5. git clean
6. git rebase
7. git merge
8. git checkout 覆盖文件
9. 删除用户未明确确认的文件

所有 Git 写操作必须由用户本人执行。

Claude Code 可以建议用户运行只读命令，例如：

1. git status
2. git diff
3. git diff --name-status

但不能替用户执行提交相关操作。

## 11. Codex 审查时机

Codex 不参与第一轮编码。

当以下条件满足后，再交给 Codex 只读审查：

1. M5-1A / M5-1B / M5-1C 至少一个小闭环完成；
2. 对应 JUnit 测试完成；
3. 本地测试通过；
4. 用户已经能解释代码；
5. git diff 中没有明显无关文件；
6. Claude Code 已停止修改。

Codex 审查重点：

1. 是否符合 system-design-v2.1.md；
2. 是否符合 schema.sql；
3. 是否越过 M5 边界；
4. 是否误写 credit_change；
5. 是否误写 appeal/report/penalty；
6. 是否旧口径回流；
7. 是否测试覆盖不足；
8. 是否可以进入 Gerrit Review。
