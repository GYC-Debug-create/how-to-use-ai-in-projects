# Autonomous Product Understanding and Local Acceptance Testing

## 一、任务目标

你不是来做普通代码审查，也不是只运行 lint、build 或已有测试。

你的任务是：

1. 阅读前后端文档和代码，理解整个系统是做什么的。
2. 自行识别系统包含的用户角色、功能、页面、接口、数据对象和业务状态。
3. 把每项功能拆成用户可以执行的动作。
4. 把动作组合为完整业务流程和状态转换。
5. 为每项相关功能设计：
   - 正常流程；
   - 替代流程；
   - 非法操作顺序；
   - 空值和错误输入；
   - 最小值、最大值、临界值和越界值；
   - 重复点击和快速操作；
   - 刷新、返回、中断和恢复；
   - 请求失败、超时和异常返回；
   - 权限、登录状态和状态持久化；
   - 并发或重复提交场景。
6. 在本地隔离副本中真实启动系统。
7. 按照真实用户或真实接口会运行的方式逐项执行测试。
8. 检查页面、接口、状态、缓存、数据库、控制台和日志是否符合预期。
9. 输出能够复现的 Bug，而不是只根据代码猜测。

例如，若系统是五子棋，应自行发现并测试开始游戏、轮流落子、重复位置、悔棋、重新开始、不同方向获胜、获胜后继续操作、棋盘边界和快速点击等，而不是等待用户列出这些功能。

本规范必须适用于当前未知类型的项目，而不是只针对上述例子。

---

## 二、原项目绝对保护

当前 `shixun12` 是原项目，只允许读取和复制。

禁止在原项目中：

- 安装或更新依赖；
- 启动前端或后端；
- 构建、测试或生成报告；
- 修改源码、配置、环境变量或数据库；
- 执行自动修复；
- 生成截图、日志、缓存、测试代码或构建产物；
- 执行 git commit、push、pull、merge、reset、clean、checkout 或 restore；
- 删除用户文件；
- 覆盖用户未提交修改。

开始时记录：

- 原项目绝对路径；
- 两个仓库各自的当前分支和 HEAD；
- 两个仓库各自的 `git status --short`；
- 两个仓库各自的 `git diff` 和 `git diff --cached` 状态摘要。

不得清理或修改用户原有未提交内容。

## 三、自动创建临时副本

必须自行完成，不要让用户手动复制。

1. 在系统临时目录创建唯一目录，例如：

   `%TEMP%\shixun12-autonomous-qa-时间戳`

2. 把整个当前 `shixun12` 工作区复制进去，必须包含：
   - `shixun12_backend`
   - `shixun12_frontend`
   - 当前尚未提交的代码和普通未跟踪业务文件。

3. 可以不复制可重新生成的目录：
   - `.git`
   - `node_modules`
   - `dist`
   - `build`
   - `coverage`
   - 缓存和日志目录。

4. 不得复制生产密钥、生产 Token、证书和明确的生产环境变量。

5. 将本文件和 `CLAUDE.md` 一并复制到临时副本，后续在临时副本执行。

6. 复制后明确确认当前命令工作目录已经切换到临时副本。

若无法安全创建临时副本，只允许继续做静态理解和测试规划，禁止在原项目运行。

## 四、先理解产品，再决定测试什么

不得一开始就盲目启动或只跑现有测试。

优先阅读：

- 根目录及两个仓库的 README；
- 需求文档、设计文档、接口文档和数据库说明；
- package.json、pom.xml、requirements.txt、构建脚本等；
- 前端路由、页面注册、菜单、导航和组件；
- 按钮、表单、事件处理函数、快捷键和交互入口；
- 后端路由、Controller、Service、模型、Schema 和数据表；
- API 请求封装和前后端类型定义；
- 登录、鉴权、角色和权限逻辑；
- 状态管理、本地缓存、持久化和恢复逻辑；
- 已有测试；
- TODO、FIXME、注释和错误提示。

必须在临时副本中生成：

`.autonomous-qa/project-model.md`

内容包括：

### 1. 产品用途

- 系统解决什么问题；
- 面向哪些用户；
- 用户最终可以完成什么结果。

### 2. 角色与权限

- 每种角色；
- 可以进入的页面；
- 可以执行的动作；
- 权限边界。

### 3. 功能清单

每项功能必须包含：

- 功能名称；
- 入口；
- 用户动作；
- 前置条件；
- 输入；
- 预期输出；
- 数据变化；
- 页面或状态变化；
- 关联的前端代码；
- 关联的后端接口或服务；
- 是否能在本地执行。

### 4. 状态模型

识别核心对象的状态和转换。

例如：

- 未登录 -> 已登录 -> Token 失效 -> 退出；
- 空购物车 -> 有商品 -> 提交中 -> 已下单；
- 未开始 -> 进行中 -> 成功/失败/取消；
- 草稿 -> 已保存 -> 已提交 -> 已撤回。

明确每个状态下：

- 允许哪些动作；
- 禁止哪些动作；
- 哪些条件触发转换；
- 哪些不变量绝不能被破坏。

### 5. 前后端契约

检查：

- URL 和请求方法；
- 参数名称、类型和必填性；
- 响应结构；
- 错误码；
- 鉴权方式；
- 分页和排序；
- 前端字段与后端字段是否一致。

## 五、自动生成完整测试模型

在临时副本中生成：

`.autonomous-qa/test-inventory.md`

不能只按页面列测试，必须按“能力、动作、状态转换”列测试。

每项相关功能至少考虑以下类别：

### A. 正常主流程

- 从正确初始状态开始；
- 执行完整流程；
- 验证最终页面、状态和数据；
- 验证下一步动作是否正确可用。

### B. 合法替代流程

- 可选字段填写与不填写；
- 不同合法顺序；
- 取消后重新进入；
- 返回后继续；
- 不同角色；
- 不同合法输入组合。

### C. 非法操作顺序

- 缺少前置步骤直接执行；
- 重复执行已经完成的动作；
- 完成后继续操作；
- 未登录直接访问；
- 直接输入深层路由；
- 在错误状态触发按钮或接口。

### D. 输入和校验

- 空值；
- 纯空格；
- 无效格式；
- 重复值；
- 超长；
- 特殊字符；
- 错误类型；
- 缺少必填字段；
- 前端绕过后直接调用本地接口。

### E. 真实边界

必须从代码、配置、数据库约束和需求中推导边界，不能随便编数字。

包括：

- 0、1、最大值、最大值加 1；
- 第一项和最后一项；
- 空集合和满集合；
- 恰好满足成功条件与差一步；
- 分页首尾；
- 日期、数量、长度、文件大小和类型限制；
- 权限和角色边界；
- 超时和重试边界。

### F. 重复、快速和并发

- 双击；
- 快速连续点击；
- 重复提交；
- 操作未完成时再次操作；
- 多标签页；
- 两个用户或角色同时操作；
- 旧状态下继续提交。

### G. 中断和恢复

- 操作中刷新；
- 返回上一页；
- 关闭后重新打开；
- 本地服务短暂失败；
- 请求超时；
- 请求返回错误；
- Token 失效；
- 缓存损坏；
- 部分成功；
- 失败后重试。

### H. 持久化和一致性

- 刷新后是否保持；
- 前端状态与后端数据是否一致；
- 本地缓存与服务端是否冲突；
- 重启本地服务后是否正确恢复；
- 撤销、删除、取消后是否仍残留数据。

## 六、本地环境与生产隔离

必须自行分析并建立本地运行环境。

优先级：

1. 项目已有的本地前端、后端和本地数据库；
2. 项目已有的本地 Mock 或测试配置；
3. 在临时副本中建立契约一致的本地 Mock；
4. 无法安全本地化时，只做规划和可安全执行的部分。

必须搜索并检查：

- HTTP/HTTPS 地址；
- WebSocket 地址；
- 数据库地址；
- 云函数；
- 对象存储；
- 登录服务；
- 微信服务；
- 支付、短信、邮件和上传服务；
- 环境变量；
- 生产域名和硬编码地址。

运行时只允许：

- `localhost`
- `127.0.0.1`
- `[::1]`
- 明确属于当前临时副本的本地服务

禁止：

- 生产后端；
- 线上数据库；
- 生产 Redis；
- 真实微信服务；
- 真实支付、短信、邮件或上传；
- 生产账号、Token、Cookie 和真实用户数据。

若后端无法本地启动，可以在临时副本中使用本地 Mock，但报告必须明确：

- 这是前端流程验证；
- 没有验证真实前后端联动；
- 哪些接口和状态被模拟。

不得把 Mock 测试冒充完整系统测试。

## 七、自行安装并调用成熟测试工具

在临时副本内检查现有工具，然后按项目类型选择。

### Web 前端

优先使用：

1. 项目已有 E2E 框架；
2. Playwright；
3. Playwright 官方 Test Agents：
   - planner；
   - generator；
   - healer；
4. AutoQA-Agent；
5. 已安装的 qa-skills。

允许自行在临时副本安装缺少的测试依赖。

目标不是只生成测试，而是：

- planner 根据产品模型和本地应用规划流程；
- generator 生成可运行测试；
- 实际运行；
- healer 只修复测试定位器、等待和测试代码问题；
- 不得通过降低断言来掩盖产品 Bug。

### 微信小程序

若检测到：

- `project.config.json`
- `app.json`
- WXML/WXSS
- 小程序页面目录

则使用：

- 本地微信开发者工具；
- `miniprogram-automator`；
- 项目已有的小程序自动化能力。

从以下内容推导动作：

- app.json 页面和 tabBar；
- WXML 控件；
- bindtap、catchtap、bindinput、bindchange、submit；
- 页面方法；
- 页面生命周期；
- wx.navigateTo、redirectTo、switchTab、navigateBack；
- wx.request；
- 本地缓存。

只能打开本地临时副本，禁止上传、预览到远端或调用生产服务。

### API 或 CLI

若某功能更适合直接通过接口或命令测试：

- 使用本地 API；
- 使用本地数据库；
- 使用临时测试数据；
- 验证状态码、响应、数据库变化、幂等性和错误处理。

## 八、实际执行原则

不得只给出测试计划。

每个能运行的场景必须实际执行，并验证：

- 页面内容；
- 路由；
- 按钮可用状态；
- 表单结果；
- 前端状态；
- localStorage/sessionStorage；
- 本地数据库或测试数据；
- 本地网络请求；
- 浏览器控制台；
- 后端日志；
- 操作后的下一步状态。

必须保存到临时副本：

- 截图；
- Playwright trace；
- 控制台错误；
- 网络错误；
- 服务日志；
- 失败断言；
- 测试数据；
- 精确复现步骤。

测试执行顺序：

1. 环境健康检查；
2. 主要正常流程；
3. 替代流程；
4. 非法顺序；
5. 输入与边界；
6. 重复和并发；
7. 中断与恢复；
8. 持久化和一致性；
9. 根据失败结果扩展探索测试。

不要进行没有依据的无限穷举。优先覆盖核心功能、高风险状态和真实边界。

## 九、失败分类与 Bug 确认

测试失败后先分类：

1. 产品 Bug；
2. 测试代码 Bug；
3. 本地环境问题；
4. 需求或预期不明确。

只有测试代码 Bug 可以自动修复测试。

产品 Bug 不得通过修改业务代码、放松断言或更改预期来“治好”。

确认一个 Bug 至少需要：

- 明确的预期行为来源；
- 实际行为；
- 前置条件；
- 精确步骤；
- 测试数据；
- 页面、日志、请求、状态或 trace 证据；
- 尽可能再次复现。

只根据静态代码怀疑但没有执行证据的问题，放入“潜在问题”，不能冒充已确认 Bug。

---

## 十、完成标准

不能因为首页能打开、build 成功或已有测试通过就宣布完成。

必须确认：

- 每个核心功能至少有正常流程；
- 每个重要状态转换已执行或明确说明为什么无法执行；
- 对相关功能考虑过非法顺序、边界、重复、中断和恢复；
- 前后端主要契约已核对；
- 浏览器控制台和本地网络错误已检查；
- 后端日志已检查；
- 所有失败已分类；
- 没有连接生产环境；
- 所有工作发生在临时副本；
- 原项目没有发生变化。

---

## 十一、最终输出

在临时副本中生成：

`.autonomous-qa/final-report.md`

并在对话中给出重点总结。

报告结构：

# 自主验收结果

## 1. 项目理解

- 产品用途；
- 用户角色；
- 核心功能；
- 核心状态模型；
- 前后端关系。

## 2. 环境

- 临时副本路径；
- 实际启动的前端、后端和数据库；
- 使用的工具；
- 使用真实本地后端还是 Mock；
- 明确确认未连接生产环境。

## 3. 覆盖矩阵

| 功能 | 正常流程 | 非法/错误 | 边界 | 重复/并发 | 中断/恢复 | 结果 |
|---|---|---|---|---|---|---|

## 4. 已确认 Bug

每项包含：

- 编号和严重程度；
- 功能和状态；
- 前置条件；
- 精确复现步骤；
- 预期；
- 实际；
- 证据文件；
- 可能涉及的前后端代码位置；
- 是否重复复现。

## 5. 潜在问题

只列有明确代码依据但未完成动态验证的问题。

## 6. 未验证部分

说明：

- 缺少什么；
- 为什么无法本地执行；
- 是否需要真实本地后端、账号、开发者工具或测试数据。

## 7. 完整性声明

必须明确输出：

- 原项目被修改：否；
- 生产环境被访问：否；
- 生产数据被修改：否；
- 测试在临时副本执行：是；
- 剩余本地进程：无；
- 是否完成完整前后端验证、前端加 Mock 验证或仅规划验证。

---

## 十二、结束清理

完成后：

1. 停止临时副本启动的所有进程；
2. 保留临时副本和报告，便于用户查看证据；
3. 不把任何文件写回原项目；
4. 回到原项目重新检查两个仓库：
   - 分支和 HEAD；
   - `git status --short`；
   - `git diff`；
   - `git diff --cached`。
5. 与开始状态比较并明确确认是否一致。

不要自动删除原项目中的 `CLAUDE.md` 和 `QA_AUTOTEST.md`。它们是用户主动放入的启动文件；测试结束后由用户决定是否保留或删除。
