# 斗罗大陆·武魂觉醒 — 前端框架迁移任务

## 一、项目背景

这是一个斗罗大陆主题的文字 RPG 网页游戏，目前使用**纯原生 JavaScript**开发，没有任何前端框架。项目已经有相当完整的内容和功能，但因为要持续做大，需要迁移到现代框架以提升可维护性。

### 项目规模（文字 RPG 版，即主力版本）

| 文件 | 行数 | 职责 |
|---|---|---|
| `public/game.js` | 6065 行 | 核心引擎：状态管理、UI 渲染、事件系统、路由 |
| `public/game-events-expanded.js` | 2665 行 | 283 个地点专属事件数据 |
| `public/game-data.js` | 1808 行 | 静态数据：出身/技能树/成就/结局/商店/锻造等 + 65 个基础事件 |
| `public/game-visual.js` | 1497 行 | 视觉效果：电影开场、粒子、特效、音频 |
| `public/game-combat.js` | 937 行 | 回合制战斗系统 |
| `public/save-utils.js` | 269 行 | 存档迁移、备份、校验 |
| `public/game-rules.js` | 207 行 | 游戏规则：升级、魂环等级上限等 |
| **合计** | **13448 行** | |

### 数据文件（JSON，13 个）
- 武魂 70 种 / 魂兽 30 种 + 30 变种 / 魂环 12 种 / 魂骨 31 种
- NPC 33 位 / 地点 27 个 / 武魂专属事件链 70 条 / 武魂技能 80 条
- 图片资源 225 张（~119MB），路径：`public/assets/`（其中地点图片 26 张，codex 有 27 条，1 个地点可能缺图）

### 后端
- 技术：Node.js + Express 4.x（单文件 `server.js`，139 行，唯一运行时依赖 `express ^4.19.2`）
- 存储：JSON 文件，无数据库
- API：4 个接口（存档保存/加载/列表/删除）+ 2 个静态数据接口（spirits/beasts）
- 已有安全措施：CSP、X-Content-Type-Options、Referrer-Policy、X-Frame-Options、Permissions-Policy、CORP、路径遍历防护、请求体大小限制（2MB）
- 测试：10 个测试文件（`tests/` 目录）

### 旧版本（可忽略或择机处理）
- `public/index.html` + `public/js/` 下 11 个文件（~3000 行）
- 这是早期像素 Canvas 动作 RPG 原型，当前主入口已切换到文字 RPG 版
- **本次迁移优先处理文字 RPG 版，像素版可暂不迁移**

## 二、迁移目标

### 核心目标
1. **前端从原生 JS 迁移到 Vue 3 框架**（使用 Vite 构建）
2. **建立组件化架构**，提升后续开发效率和代码可维护性
3. **引入状态管理方案**，替代当前的全局变量 + 手动 DOM 操作模式
4. **保持游戏内容 100% 不变**——剧情、数值、玩法、UI 外观全部保持原样
5. **所有现有测试必须通过**，存档兼容性不能断

### 非目标（本次不做）
- 不加新功能、不改游戏内容
- 不做视觉重设计
- 不迁像素 Canvas 版（`public/js/` 目录的旧版）
- 不改后端语言和框架（Node.js + Express 继续用）

## 三、技术选型建议

### 前端框架：Vue 3 + Vite
- **为什么选 Vue 3**：项目现有代码大量使用 `G.hp += 10` 这种直接 mutation 模式，Vue 3 的 `reactive()` 原生支持可变状态，迁移时状态修改逻辑改动最小；同时 Vue 的 `<template>` 基于 HTML，现有 `game.html` 的结构可以大部分直接搬入，不需要像 JSX 那样全部重写
- **构建工具**：Vite（Vue 官方推荐，配置简单，开发体验好）
- **语言**：JavaScript 即可，不强制 TypeScript（避免迁移期同时处理类型系统）

### 状态管理：Pinia
- 替代当前的 `var G = null` 全局变量模式
- 为什么不是 Vuex：Pinia 是 Vue 3 官方推荐方案，API 更简洁，TypeScript 支持更好，没有 mutations/getters/modules 的样板代码
- 状态分片：usePlayerStore / useCombatStore / useUiStore / useEventStore / useGameStore
- Pinia 的 `state` 允许直接 mutation（`store.hp += 10`），和现有代码风格一致

### 样式方案：`<style scoped>` + 现有 CSS 变量
- 现有的 `css/tokens.css`（设计 token）直接复用
- 组件级样式用 Vue SFC 的 `<style scoped>`，自动隔离作用域，避免样式冲突
- 全局样式（主题、滚动条等）保留在全局 CSS 中

### 路由：Vue Router
- 当前是 hash 路由（`#/title`、`#/game`、`#/map`、`#/codex`）
- 迁移到 Vue Router，保持 URL 结构不变

## 四、后端是否需要改善？

### 结论：**需要，但不需要重写，做增量改善即可。**

### 必须改善的问题（P0）

| 问题 | 风险 | 改善方案 |
|---|---|---|
| **存档 API 无鉴权** | 任何人可以读/改/删别人的存档 | 加简单的 token 鉴权：创建存档时生成 token，后续操作携带 |
| **多标签页覆盖写** | 同时开两个标签页玩，存档会互相覆盖 | 加乐观锁（lastSave 时间戳比对）+ 冲突提示 |
| **服务器存档无历史版本** | 存档损坏无法回滚 | 每次保存时保留最近 5 个历史版本 |
| **无请求限流** | 容易被刷接口 | 加 express-rate-limit，每个 IP 每分钟 60 次 |

### 建议改善的问题（P1）

| 问题 | 改善方案 |
|---|---|
| 存档直接写磁盘，并发写入可能损坏 | 加写入队列 / 用 fs.writeFileSync 已经是同步的，但建议加文件锁 |
| 静态资源无缓存头 | 加 etag / cache-control，图片资源长期缓存 |
| 没有日志系统 | 加简单的访问日志和错误日志（morgan + winston 或直接 pino） |
| 没有健康检查接口 | 加一个 `/api/health` 返回状态 |

### 不需要改的
- **语言/框架不变**：Node.js + Express 完全够用，不需要换成 NestJS / Fastify / Go / Python 之类的
- **不需要数据库**：JSON 存储对于这个规模和类型的游戏是合理的，换成 SQLite 或 MongoDB 收益不大，反而增加部署复杂度
- **不需要微服务**：单体完全够用

## 五、迁移步骤（分阶段执行）

### 第一阶段：基础设施搭建
1. 初始化 Vite + Vue 3 项目
2. 配置目录结构：
   ```
   src/
   ├── components/     # 可复用组件（.vue）
   ├── pages/          # 页面级组件（标题页/游戏页/地图页/图鉴页）
   ├── stores/         # Pinia 状态管理
   ├── data/           # 静态数据（从 JSON 和 game-data.js 迁移）
   ├── engine/         # 纯逻辑层（战斗计算、规则计算、事件处理）
   ├── composables/    # 自定义 composables（useXxx）
   ├── utils/          # 工具函数
   ├── styles/         # 全局样式 + tokens
   └── App.vue / main.js
   ```
3. 把现有静态资源（`public/assets/`、`public/data/*.json`）接入
4. 配置 Vue Router，4 个页面路由先做空壳
5. 跑通开发环境和生产构建

### 第二阶段：纯逻辑层迁移
**这一层不涉及 UI，纯函数，最容易迁**
1. 迁移 `game-rules.js` → `src/engine/rules.js`
2. 迁移 `game-combat.js` 的战斗计算逻辑 → `src/engine/combat/`
   - 伤害计算、元素克制、暴击连击等纯计算函数先迁
   - 战斗流程控制（回合循环）稍后迁
3. 迁移 `save-utils.js` → `src/engine/save.js`
4. 迁移 `game-data.js` 的静态数据 → `src/data/`
   - 出身（ORIGINS）、技能树（SKILL_TREE）、成就（ACHIEVEMENTS, 72 个）、称号（TITLES, 41 个）、结局（ENDINGS, 27 个）、商店（SHOP_ITEMS）、锻造配方（FORGE_RECIPES）等数据
   - EVENTS 基础事件数据（65 个）
5. 迁移 `game-events-expanded.js` → `src/data/events-locations.js`（283 个地点扩展事件）
6. **这一步结束后，所有纯逻辑应该都有对应的单元测试，且全部通过**

### 第三阶段：状态管理搭建
1. 设计 Pinia store 结构：
   - `usePlayerStore`：玩家属性、等级、魂环、背包、技能点
   - `useCombatStore`：战斗状态、敌我双方数据
   - `useEventStore`：当前事件、选项、事件历史
   - `useUiStore`：弹窗、通知、引导、设置
   - `useGameStore`：游戏阶段、时间、地点等全局状态
2. 把 `game.js` 里的 `G` 对象拆解到各个 store（Pinia state 支持直接 mutation，`G.hp += 10` 可直接迁移为 `playerStore.hp += 10`）
3. 实现存档的序列化/反序列化（store → 存档对象 → store）

### 第四阶段：UI 组件迁移（工作量最大）
**按照"从外到内、从简单到复杂"的顺序迁**

1. **通用组件**：按钮、弹窗、进度条、通知 toast、头像框
2. **标题页**（`#/title`）：最独立，先迁
3. **创建角色页**：名字输入、出身选择、武魂觉醒
4. **游戏主界面**：
   - 顶部状态栏（HP/魂力/等级/金币）
   - 主菜单（状态/背包/技能/魂环/社交/地图/图鉴/设置）
   - 剧情文本区 + 选项按钮
   - 这是核心，可能要拆成 2-3 天
5. **战斗界面**：血条、技能按钮、战斗日志、胜负结算
6. **地图页**（`#/map`）：地点标记、旅行、迷雾
7. **图鉴页**（`#/codex`）：6 类图鉴的标签切换和列表
8. **其他弹窗**：背包、技能树、魂骨、NPC 列表、商店、锻造、挑战塔、签到

### 第五阶段：视觉和动效迁移
1. 迁移 `game-visual.js` 的 CinematicEngine（电影开场）
2. 迁移粒子效果和过渡动画
3. 确保 CSS 变量、主题色和原版完全一致

### 第六阶段：联调与测试
1. 完整走一遍游戏流程：创建角色 → 觉醒 → 序章 → 第一个事件 → 第一场战斗 → 第一次猎环
2. 跑通所有现有测试（10 个测试文件），必要时改造测试以适配新架构
3. 测试存档兼容性：用旧版生成的存档在新版中能否正常读取
4. 测试响应式：手机/平板/桌面三种尺寸
5. 性能测试：首屏加载时间、事件切换流畅度

### 第七阶段：后端增量改善
1. 加 token 鉴权
2. 加乐观锁防覆盖
3. 加存档历史版本
4. 加请求限流
5. 加缓存头和健康检查接口

## 六、关键注意事项

### 1. 内容绝对不能变
- 所有剧情文本、数值、事件逻辑必须**逐字逐句**保持一致
- 迁移过程中如果发现 bug，**不要顺手修**，记下来单独处理，避免引入不可控的变化
- 建议用截图对比的方式验证 UI 一致性

### 2. 存档兼容性是红线
- 旧版存档（本地 localStorage 和服务器 JSON）必须能在新版中正常读取
- 旧存档迁移逻辑（`save-utils.js` 的 migrateSave）要完整保留
- 新版存档格式如果有变化，要保证向前兼容

### 3. 渐进式迁移，随时可回退
- 建议在迁移过程中保持"新旧两套代码都能跑"的状态
- 可以先迁一个页面验证方案可行性，再铺开
- 用 feature flag 控制新旧版本切换

### 4. 逻辑和渲染分离
- 迁移过程中要强制"纯逻辑层"和"UI 层"分离
- 战斗计算、事件处理、规则判定全部放在 `src/engine/` 下，是纯函数，不依赖 Vue
- 这样未来即使换框架，逻辑层也不用动

### 5. 像素版怎么办？
- 像素 Canvas 版（`public/js/` 下的旧版，11 个文件）本次可以**完全不动**
- 保留 `/index.html` 入口，让它继续工作
- 等文字版迁完、稳定了，再决定像素版是迁、是弃、还是重写

## 十、开始之前请先确认

确认无误后，就从第一阶段（基础设施搭建）开始。
